# miyf 原生三端 · 设计与开发提示词

> 版本：v1.0 · 2026-09-19  
> 范围：安卓 / iOS / 鸿蒙 NEXT 的界面生成提示词，以及鸿蒙一期工程开发提示词  
> 视觉基线对齐：`design/miniapp-redesign.html`  
> 业务 API 对齐：`miniapp/src/api/*`、`server/` 个人端 Controller  
> 鸿蒙工程：`harmony/`（一期食客主链路已落地）

## 怎么用

### UI 设计（三端共用基线）

1. 每次生成前先贴 **§1 共享基线**。
2. 再贴 **§2 Android**、**§3 iOS** 或 **§4 鸿蒙** 其中一段。
3. 一次只出 4～6 屏。先出登录、角色、食客首页、厨师工作台、健康总览，确认气质后再补其余屏。
4. 三端信息架构、文案和配色保持一致；只在导航、控件和系统能力上按各端规范分开画。

### 工程开发（当前先做鸿蒙）

1. 开发前贴 **§5 总控**。
2. 再只贴当前这一期（一期见 **§5.1**）。不要一次把多期都丢进去。
3. 安卓、iOS 以后只换 UI 与登录方式，接口契约以 `harmony/entry/src/main/ets/api` 的方法名和路径为准。

## 1. 共享基线（三端 UI 必贴）

```text
你是 miyf 的产品界面设计师。miyf 是面向家庭和小团队的内部厨房预约与健康数据产品，品牌名 miyf，两个房间分别叫「胡闹厨房」「胡闹健康」。平台内没有价格、购物车金额、优惠券、支付、下单交易。预约是「今天吃什么」，不是外卖。

用户：同一账号可在「厨师 / 食客」间切换。厨师经营一个厨房：菜品、菜谱、分类、库存、邀请码、审核食客绑定、处理预约。食客用邀请码加入一个厨房，浏览在售菜、加入预约草稿、提交预约、完成后评价。健康是独立模块，可从顶部服务切换进入：看指标、趋势、数据源同步。健康内容只是生活方式参考，禁止诊断、用药、就医结论的视觉和文案。

视觉（必须严格使用，不要换成通用蓝紫 SaaS）：
- 页面底 #FFFDF8 奶油色；主文案 #2B2622；次文案 #8A8178；弱文案 #B5AC9F；分割线 #F1E9DD
- 厨房主色渐变 #FFB36B → #F07B1F，浅底 #FFF1E2 / #FFF8EF
- 健康主色渐变 #5FCFAE → #18A885，浅底 #E7F7F0 / #F4FBF8
- 状态：正常/完成 #18A885；待处理/需关注 #D99426；异常/驳回 #E15A4B；进行中 #4A90D9。各自配浅底，不要纯色大面积铺满
- 卡片白底、描边 #F1E9DD、圆角 20；输入框圆角 12；胶囊 Tab / 标签圆角全圆
- 主按钮用对应模块渐变，字重 600，不要扁平纯色商务按钮
- 阴影很轻：0 8px 24px rgba(80,50,10,.08)
- 中文用系统黑体（苹方 / 思源 / 鸿蒙黑体），口语、生活化，禁止营销腔（「爆款」「限时」「立即抢」）
- 图标用简洁线性图标，不要用 emoji 当正式图标；食物摄影用暖色真实照片，不要插画卡通、不要 3D 玻璃拟态

信息架构（三端相同，不要增删一级入口）：
食客底部四栏：首页、菜品、预约、我的。
厨师不走这四栏，进入「厨房工作台」：宫格为菜品、菜谱、分类、预约、食客申请、邀请码、厨房资料。
顶部始终有「厨房 / 健康」切换，切换后主题色从橙变为薄荷，布局骨架不变。
健康不进底部四栏，作为服务切换后的首页。

必须覆盖的屏幕与内容（文案用下面的真实示例，不要 lorem）：
1. 登录：手机号 + 验证码。可选第三方只作为次要入口，不是唯一登录。无微信支付。
2. 选身份：两张大卡「我是厨师」「我是食客」，副文案说明各自能做什么。
3. 加入厨房：输入 6 位邀请码；状态分未绑定、待确认、已绑定、未通过。
4. 食客首页：厨房名「老王的灶」、今日推荐大卡（红烧肉、清蒸鲈鱼）、库存将尽提示、底部常驻预约条「已选 3 样 · 去预约」。入口「说一句话点菜」。
5. 菜品列表：分类胶囊（荤菜、素菜、汤羹、主食、凉菜），左图右文，库存「今日还剩 8 份」。
6. 菜品详情：封面、名称、一句话、口味标签、库存步进器、菜谱步骤、评价。主按钮「加入预约」，不是「购买」。
7. 预约：草稿（明天 12:00 午餐 · 2 人 · 少辣）与历史单。状态条：待确认 → 已确认 → 备餐中 → 可取餐 → 已完成。可取消。无金额。
8. 评价：星级 + 短评，完成后才出现。
9. 我的：头像昵称、当前身份、绑定厨房、切换厨师/食客、退出。
10. 厨师工作台：问候「下午好，老王」、厨房名、四格数据（待确认 5、备餐中 3、在售 12、食客 28）、宫格带角标、最新一条待处理预约可直接确认/驳回。
11. 菜品管理：搜索、状态胶囊（在售 / 审核中 / 草稿 / 已下架）、库存与上架下架。主操作「新建」，次操作「用文字生成」。
12. 处理预约：三块汇总 + 流程节点 + 确认、开始备餐、标记可取、完成。
13. 厨房资料：封面、名称、简介、邀请码可复制。
14. 食客申请：待确认列表，通过 / 拒绝。
15. 健康总览：评分环 86、「状态不错，继续保持」、需关注横幅（血压偏高）、指标卡（心率 72 bpm、血氧 98%、睡眠 7.2 小时、步数 8432、体重 62.5 kg），每卡一条小趋势。
16. 指标详情：折线、参考区间带、平均/最低/最高/记录数。异常用琥珀或红标出，不弹恐吓框。
17. 数据源：华为健康已连接 / 未连接，手动同步，上次同步时间。失败给「暂不可用」，不空白。
18. AI 建菜：输入框粘贴文本或链接；结果是可编辑草稿列表（名称、分类、库存默认 10），主按钮「提交审核」，不是直接上架。识别失败回到空白表单。
19. AI 点菜：只匹配当前厨房在售菜。匹配到的可改数量；对不上的放「没找到」列表，禁止编造菜名。
20. AI 饮食参考卡嵌在预约页：结论三档（合适 / 需注意 / 不建议），逐菜标签，一句可执行建议，固定小字免责：「以上为一般性饮食参考，不构成医疗建议」。分析失败则整张卡不出现，预约仍可提交。

状态与空态：加载用奶油底骨架屏；空态一句话加一个动作（去加入厨房、去建第一道菜、去连接数据源）；错误可重试。所有写库动作都要人点确认。

输出：高保真手机界面，简体中文，状态栏与系统导航按该平台真实样式。每屏左上角标编号（如 D1、K1、H1）。不要水印，不要价格，不要英文占位按钮。
```

## 2. Android UI

```text
在 miyf 共享基线之上，按 Android 手机（360×800 dp，手势导航）出一套界面。遵循 Material 3 的间距、触控和动效，但品牌色锁定，不要用壁纸动态取色覆盖灶橙和薄荷绿。

平台控件：
- 食客用底部导航 4 项：首页、菜品、预约、我的。图标 24dp，选中用当前模块主色，未选中 #B5AC9F。
- 厨师工作台是独立目的地，从「我的 → 进入厨房」进入，自带返回，不用底部四栏。
- 顶部用小标题栏，滚动后可收成一行。搜索用栏内搜索，不要单独做一个只有搜索框的页面当首页。
- 主操作用右下角 FAB：食客首页是「说一句话点菜」，菜品管理是「新建菜品」。FAB 用模块渐变，不要默认紫色。
- 列表是卡片列表，卡片间距 12dp，左右边距 16dp。点击有水波纹，水波纹颜色用主色 12% 透明。
- 确认、驳回、退出用底部对话框， destructive 用 #E15A4B。返回支持预测性返回手势。
- 状态栏浅色图标，背景与奶油底融合，edge-to-edge，内容避开手势条。
- 字号：标题 22sp、区块 16sp、正文 14sp、说明 12sp。最小点击区域 48dp。

系统能力只在对应屏出现，不要做成功能堆砌：
- 数据源页增加「Health Connect」，与「华为健康」并列，展示已授权范围（步数、心率、睡眠、体重），可撤销。
- 预约进行中可用一条简短通知样式示意：备餐中 / 可取餐。不要做复杂通知中心页。
- 只画直板手机。折叠屏和平板不要在这版出现。

先出这 6 屏：登录、食客首页、菜品详情、预约（含 AI 饮食参考卡）、厨师工作台、健康总览。其余屏等这 6 屏确认后再画。
```

## 3. iOS UI

```text
在 miyf 共享基线之上，按 iPhone（390×844 pt，带 Home Indicator）出一套界面。遵循 iOS Human Interface Guidelines：大标题、底部 Tab、页面栈从右推入、边缘右滑返回、半屏 Sheet。不要用 Material 的 FAB、水波纹、抽屉导航。

平台控件：
- 食客 Tab Bar 四项：首页、菜品、预约、我的。选中色为当前模块主色，背景白，顶部分割线用 #F1E9DD，不要默认 iOS 蓝。
- 一级页用大标题（滚动后收成导航栏标题）。二级页标准导航栏，左侧返回是文字旁的 chevron，不要自绘一个圆形返回按钮。
- 「说一句话点菜」「新建菜品」「筛选」用底部 Sheet，带抓手，可拉到全屏。不要用 Android FAB。
- 主按钮贴在安全区上方，高 50pt，圆角 14，全宽，左右 16pt。次操作用文字按钮或浅底胶囊。
- 列表用 inset grouped 的观感，但卡片仍是白底圆角 20、轻描边，不要系统默认灰分组底把奶油底冲掉。
- 开关、步进器可以是 iOS 形态，着色用模块主色。
- 破坏性操作（退出、解除绑定、驳回）用 Action Sheet，红色仅用于破坏项。
- 状态栏时间 9:41，深色文字；底部 Home Indicator 深色细条。内容避开刘海和底部安全区。
- 字体：中文苹方，英文与数字 SF Pro。标题 22/700，正文 15/400，说明 13/400。

只在这些位置体现苹果能力，其余屏保持克制：
- 预约详情顶部用一条灵动岛 / Live Activity 示意：左侧小锅图标，中间「备餐中」，右侧「约 12:30 可取」。不要做复杂动画分镜。
- 数据源页用「健康 App（HealthKit）」卡片，说明仅读取步数、心率、睡眠、体重，可停止授权。不要出现医疗诊断。
- 登录主路径仍是手机号验证码；「通过 Apple 登录」只作为次按钮，黑色胶囊，放在主按钮下方。
- 只画 iPhone 竖屏，不要 iPad，不要深色模式。

先出这 6 屏：登录、食客首页、菜品详情（Sheet 已收起，底部是加入预约）、预约、厨师工作台、健康总览。
```

## 4. 鸿蒙 UI

```text
在 miyf 共享基线之上，按 HarmonyOS NEXT 手机（360×780 vp，底部手势条）出一套界面。遵循鸿蒙设计：大圆角卡片、底部页签、标题栏返回、轻模糊只用于浮层。不要做成 Android Material，也不要做成 iOS。字体用鸿蒙黑体，数字等宽对齐。

平台控件：
- 食客底部页签 4 项：首页、菜品、预约、我的。选中用模块主色，页签背景 #FFFFFF，顶边 #F1E9DD。
- 一级页标题居左加粗 20vp；二级页标题居中，左侧返回箭头。不要用 iOS 大标题，也不要 Material 小标题居中加 FAB。
- 主按钮高 48vp、圆角 16vp、左右边距 16vp，贴在手势条之上。列表主操作放标题栏右侧文字按钮（「新建」），不要悬浮 FAB。
- 卡片圆角 20vp，间距 12vp。宫格用 4 列，图标底是 52vp 圆角方块，角标是红底白字小胶囊。
- 半模态用于「说一句话点菜」和筛选，顶部小横条，背景轻微模糊，内容区仍是奶油色，不要整页毛玻璃。
- 对话框用于确认/驳回：圆角 24vp，主按钮在右。
- 状态栏与页面同色，深色图标，内容避开状态栏和底部手势区。
- 触控热区不小于 40vp。动效短、柔和，150–250ms，不要弹跳夸张。

鸿蒙特有，只画这些，不要扩展成万能设备：
- 数据源页把「华为运动健康」放第一位：未连接时主按钮「去授权」；已连接时显示授权范围、上次同步 08:30、按钮「立即同步」「解除授权」。这是该端的差异点，视觉上比其他数据源更完整，但仍用健康薄荷色，不要换成华为红。
- 另给 1 张 2×2 服务卡片示意，放在设计稿旁，不要画进 App 页面里：奶油底，标题「老王的灶」，一行「备餐中 · 约 12:30 可取」，下方小字「红烧肉 ×1」。卡片用灶橙点缀，不要信息过载。
- 健康总览可在评分环旁加一行「数据来自华为运动健康 · 今天 08:30」。
- 只画直板手机竖屏。不做手表、折叠屏、平板、跨设备流转。

先出这 6 屏，外加 1 张服务卡片：登录、食客首页、预约、厨师工作台、健康总览、数据源。
```

## 5. 鸿蒙工程开发 · 总控

> 三端后续都要开发；当前优先鸿蒙。业务规则继续放在现有服务端，安卓和 iOS 以后只换界面和登录方式。

```text
你在现有 miyf 仓库里新增鸿蒙 NEXT 客户端，目录 harmony/。技术栈只允许 HarmonyOS NEXT、ArkTS、ArkUI、Stage 模型。禁止 Java/JS 的 FA 模型，禁止 Flutter、React Native、uni-app 套壳。不要改小程序 miniapp/、管理端 miyf-admin/ 的页面。服务端只允许为「登录方式」做增量，厨房、预约、健康、AI 的业务规则已在 server/ 里，客户端不得重写。

三端约定：鸿蒙、安卓、iOS 都是薄客户端。可复用的是接口契约，不是 ArkTS 源码。以后安卓用 Kotlin、iOS 用 Swift 各自写 UI，按 harmony/entry/src/main/ets/api 的方法名和路径照搬。因此：
- HTTP、DTO、仓库放在 api/ 与 repository/，不引用任何 ArkUI 组件。
- 华为账号、浏览器打开授权页、服务卡片，只放 platform/，仓库通过接口调用。
- 页面只做展示和调用仓库。状态机、是否可取消、AI 是否降级，以服务端结果为准，客户端不发明新状态。

接口事实（先读代码再写，禁止猜字段）：
- 基址默认 https://www.miyf.cn，开发环境可配置。个人端路径前缀 /api，对齐 miniapp/src/api。
- 响应包络 { code, message, data }。code 为 0 才成功，上层只拿 data。HTTP 401 或 code 40100：清 token，回登录页。
- Header：Authorization: Bearer <token>。token 与过期时间存 Preferences，提前 60 秒视为过期。
- 雪花 ID 在 JSON 里已是字符串。客户端一律 string，禁止 number。
- 图片若是 /r/{id} 或 /api/r/{id}，拼到基址上再显示。
- 对照这些文件，不要对照管理端 /api/admin/**：
  miniapp/src/api/auth.ts、kitchen.ts、dish.ts、order.ts、comment.ts、health.ts、ai.ts
  miniapp/src/types/index.ts
  server 中 personal 包下的 Controller

登录是阻塞项，必须先做完再写业务页。现在只有 POST /api/auth/wx-login，那是微信小程序用的，鸿蒙不要调用它冒充登录，也不要接管理端 /api/admin/auth/login。
在 auth-service 增加 POST /api/auth/huawei-login：用华为账号 authorization code 换 openId/unionId，必要时带手机号。签发与 wx-login 相同的 LoginVo（token、expireSeconds、userId、displayName）。用户落到现有 AppUserAccount，华为身份与 wechatId 并列，禁止新建第二套用户表。同一手机号合并到同一用户，这样以后微信、安卓、iOS 还是这个人。配置项风格对齐现有 HUAWEI_HEALTH_*，不要把 clientSecret 放进客户端。客户端用 Account Kit 取 code，失败时给出可读错误，不要白屏。
手机号验证码登录这次只预留注释，不实现。安卓、iOS 以后只新增登录入口，登录成功后的 token 和 /api/user/me 不变。

业务边界：
- 没有价格、购物车金额、支付。按钮写「加入预约」「提交预约」，不写「购买」。
- 角色：POST /api/user/me/role 首次开通，PUT /api/user/me/role 切换。厨师与食客页面分开。一客一厨。
- 预约状态只允许：PENDING→CONFIRMED，CONFIRMED→PREPARING，PREPARING→READY，READY→COMPLETED。食客取消只允许 PENDING→CANCELLED。厨师用 PUT /api/chef/orders/{id}/status，食客用 POST /api/orders/{id}/cancel。
- AI 只产草稿。建菜结果要人确认后才走现有提审，不直接上架。点菜只能匹配当前厨房在售菜，unmatched 必须展示，禁止编造菜名。饮食分析失败时不显示卡片，不挡住提交。免责声明用接口返回的 disclaimer，没有则用「以上为一般性饮食参考，不构成医疗建议」。
- 健康同步走现有服务端：GET /api/health/providers/huawei/authorize-url，系统浏览器打开，完成后轮询 GET .../oauth/status。禁止调用已废弃的 POST .../oauth/callback。不要在端上用 Health Kit 另做一套上报。

视觉：页面底 #FFFDF8，主字 #2B2622，次字 #8A8178，线 #F1E9DD。厨房渐变 #FFB36B→#F07B1F，健康渐变 #5FCFAE→#18A885。卡片白底、圆角 20、轻描边。中文口语，不要营销腔。底部四栏只给食客：首页、菜品、预约、我的。厨师从「我的」进工作台，工作台没有这四栏。顶部可在厨房与健康之间切换，切换后只换主题色和首页，不换账号。

工程要求：网络层一个 ApiClient。空、加载、错误三态都要有，错误用服务端 message。不要写大而全的抽象基类。每期结束保证能编译，并列出已接通的接口。不要提交密钥。
```
